## Section 1. 내보내기·공유 표면 — 새 답 형태 4종 전부에서 결함 확인

### ① 시군구 합산 결과 — 화면·CSV·MD 전부 "행정동"·"20개"로 나옴

```
[고령비율 높은 시군구] 화면 20행 · CSV 본문 20행 (기대 22)
  CSV 머리글: 순위,행정동코드,시도시,이름,값,비고   ← "행정동코드"
  CSV 1행 코드: 4885000000 (10자리 — 시군구 5자리가 아니라 dong 코드를 0으로 패딩한 형태)
  MD 요약줄: "대상 행정동 20개 중 상위 10개 제시"   ← "시군구"가 아니라 "행정동"
```

이건 export 레이어만의 문제가 아니라 **화면 결과 패널 자체가 이렇게 표기한다.** 5개 공공 sgg 지표(총인구·고령비율·세대수·출생·1인가구) 전부 동일하게 재현했다:
```
[고령비율 높은 시군구] 패널: "20개 행정동을 고령인구 비율 높은 순으로 정렬했습니다."
[총인구 많은 시군구]   패널: "20개 행정동을 총인구 많은 순으로 정렬했습니다."
[세대수 많은 시군구]   패널: "20개 행정동을 기준월 세대 수가 많은 순서로 정렬했습니다."
[출생 많은 시군구]     패널: "20개 행정동을 기준월 출생 수가 많은 순서로 정렬했습니다."
[1인가구 많은 시군구]  패널: "20개 행정동을 1인가구 비율이 높은 순서로 정렬했습니다."
```
상단 `query-notice`는 매번 정확히 "시군구"라고 말하는데, 그 아래 결과 패널 자체가 만드는 요약문("20개 행정동을 ~") 은 여전히 "행정동"이라고 말한다 — **같은 화면 안에서 두 문장이 서로 모순된다.** `regionUnitLabel()`(export-csv.ts:54)이 코드 자릿수로 단위를 가리는 방식은 맞지만, 그 결과가 CSV/MD에만 적용되고 화면 패널 자체의 요약 생성 로직에는 반영되지 않은 것으로 보인다 — 혹은 패널 요약문이 애초에 export와 다른 별도 함수에서 만들어지며 그쪽은 이 판별을 아예 안 하는 것으로 보인다(정확한 함수는 못 찾았다 — UI 쪽 코드를 더 봐야 확정 가능).

**행 수도 22가 아니라 20이다.** 문서는 "기본 20행만 보이므로 더 보기를 눌러 끝까지 세라"고 가정했는데, 실제로 **"더 보기" 버튼 자체가 없다.** 5개 지표 전부 화면에 20행만 뜨고 그 이상 볼 방법이 없다 — 22개 시군구 중 2개가 화면에서도, CSV에서도 조용히 빠진다.

### ② 새로 발견 — "방법론" 패널이 공공 도구 전체에서 얼어붙어 있다 (sgg 여부 무관)

sgg를 조사하다 우연히 발견했다. 민간 큐브 레이어는 질의를 바꾸면 "방법론" 문구가 정확히 바뀐다:
```
[카드매출 높은 지역] 방법론 · 카드매출 = 전체카드 이용금액 월 합계(전수화) · ...
[평균소득 높은 동]   방법론 · 평균소득 = 연령구간 월소득 평균의 인구가중 평균 · ...
[생활인구 많은 동]   방법론 · 총생활인구 = 월 전체 시간대 평균 생활인구 · ...
```
그런데 **공공 도구(tool-registry 경로)는 무엇을 물어도 항상 첫 데모 화면의 "의료취약지수" 공식만 보여준다** — sgg든 행정동이든 무관하다:
```
[총인구 많은 시군구]  방법론 · 의료취약지수 = 공급 부족 35% + 고령 수요 25% + 최근접 거리 25% + 2km 무시설 15%. …
[세대수 많은 시군구]  방법론 · 의료취약지수 = 공급 부족 35% + 고령 수요 25% + 최근접 거리 25% + 2km 무시설 15%. …
[총인구 많은 동]      방법론 · 의료취약지수 = 공급 부족 35% + 고령 수요 25% + 최근접 거리 25% + 2km 무시설 15%. …
[세대수 많은 동]      방법론 · 의료취약지수 = 공급 부족 35% + 고령 수요 25% + 최근접 거리 25% + 2km 무시설 15%. …
[고령화율 높은 동]    방법론 · 의료취약지수 = 공급 부족 35% + 고령 수요 25% + 최근접 거리 25% + 2km 무시설 15%. …
```
sgg·행정동 5개 조합, 총인구·세대수·고령화율 등 서로 다른 지표 전부 동일하게 "의료취약지수" 공식만 표시했다. **이건 이번 세션의 sgg 작업과 무관한, 훨씬 이전부터 있었을 공공 도구 전반의 결함이다.** 사용자가 "세대수 많은 동"을 물었는데 화면 하단엔 전혀 관련 없는 의료취약지수 가중치 공식이 붙어 나온다 — 오도성이 크다.

### ③ 비율 조건(%) — CSV는 필터를 무시하고 전체 305행을 내보낸다

```
[상위 10% 소득 지역] 화면 31행 (정상 필터링됨)
  CSV 본문: 305행 ← 필터 무시, 전체 데이터셋을 그대로 냄
  MD 요약줄: "대상 행정동 305개 중 상위 10개 제시" ← 31이 아니라 305
```
화면은 맞게 31개로 좁히는데, CSV·MD 내보내기는 **필터링 이전의 전체 305행**을 내보낸다. 화면과 파일이 서로 다른 답을 준다 — 사용자가 화면에서 확인하고 다운받으면 완전히 다른(더 많은) 데이터를 받는다.

### ④ 공유 링크 — sgg·비율 조건 둘 다 복원되지 않는다 (평범한 질의는 정상)

대조군(평범한 행정동 질의)은 정상 복원됨을 먼저 확인:
```
[대조군] "평균소득 낮은 동" → 공유 링크 복원 ✓ 결론 일치
[대조군] "창원 생활인구 많은 동" → 공유 링크 복원 ✓ 결론 일치
```
그런데 이번 세션에서 새로 생긴 두 답 형태는 둘 다 깨진다:
```
[시군구] "고령비율 높은 시군구"
  링크: ?tool=rankElderlyRatio&region=4885000000&radius=2&q=고령비율+높은+시군구
  복원 결과: "표시할 순위·시설이 없습니다. 빠른 분석이나 질문을 다시 실행해 보세요."
  → 완전히 빈 화면으로 복원됨

[비율] "상위 10% 소득 지역"
  링크: ?tool=rankElderlyRatio&region=4817075000&radius=2&q=상위+10%+소득+지역
  복원 결과: "진주시 충무공동이 고령화율에서 가장 두드러집니다."
  → 원래 질의(평균소득 상위 10%)와 전혀 무관한 답(고령화율)으로 복원됨
```
공유 링크는 `tool`(고정값처럼 보이는 `rankElderlyRatio`가 두 경우 모두 박혀 있다 — 우연인지 항상 이 값인지는 못 봤다)·`region`(단일 지역 코드)·`radius`(이 질의들과 무관한 기본값 2)·`q`(원문 텍스트)만 담는다. **비율 필터·sgg 단위 같은 구조화된 조건은 URL에 전혀 실리지 않고, 열었을 때 원문 텍스트를 자연어 파서에 다시 태우는 방식**으로 보인다 — 그 결과가 원래 화면과 다르거나(2번째 사례) 아예 빈 값(1번째 사례)이 된다. 문서가 우려한 "예전에 민간 결과가 공유 링크로 복원되지 않던 결함"이 새 답 형태에서 그대로 재발했다.

### ⑤ 부가 발견 — 2지표 동반 표시가 CSV/HWP에는 담기지 않는다

```
[고령비율 상승하는 동] 화면·코드: metric() 2개(고령비율 12개월 변화 %p + 고령인구 비율 %) 첨부됨
  CSV 1행: "고령비율 12개월 변화 · 0.06%p"만 있고 "고령인구 비율"은 없음
  HWP도 동일 — %p는 있는데 두번째 지표는 없음

[세대수 많은 동] 화면 안내: "세대당 인구를 함께 보세요"라고 말은 하지만
  CSV 1행: "세대 수 · 25,543세대"만 있고 "세대당 인구" 값 자체는 없음
```
`tool-registry.ts`의 `rankElderlyRatioTrend`/`rankHouseholdCount`는 코드상 `analysisRegion(region, score, [metric1, metric2])`로 지표 2개를 함께 붙이는데, CSV/HWP로 나가는 `row.note`에는 **첫 번째 지표만 남고 두 번째는 사라진다.** 화면 안내 문구는 "함께 보세요"라고 약속하지만 실제로 함께 나오는 건 export가 아니라 화면 패널의 상세 펼침 뷰뿐인 것으로 보인다(정확한 렌더 위치는 확인 못함 — CSV/HWP 파이프라인에서만 확인).

### ⑥ 값 조건 고지 — 정상, 단 자기 검증에서 한 번 오탐 있었음(자체 발견)

```
[소득 100만원 이상인 동] MD/HWP에 고지 문구 정상 포함
```
1차 시도(`.prod-surfaces3.mjs`)에서는 `query-caveat` 텍스트를 빈 문자열로 읽어 "포함 여부"를 빈 문자열 포함 검사로 처리하는 바람에 **자동으로 통과 처리되는 자기 판정 버그**가 있었다. 원인은 직전 질의("고령비율 높은 시군구")에서 이 질의로 넘어오는 레이어 전환이 일반 대기시간(1.8~2.5초)보다 오래 걸려 캡처 타이밍을 놓친 것으로 추정된다(같은 세션에서도 재현/미재현이 갈렸다). 별도로 이 질의 하나만 단독 실행했을 때는 고지 문구가 정상적으로 화면·MD·HWP 모두에 나타남을 확인했다 — **결함이 아니라 내 스크립트의 타이밍·자기검증 결함**으로 판단한다.

### ⑦ 답 없는 상태("주말") 내보내기 — 직전 결과를 그대로 내보냄, 경고 없음

```
"주말에 사람 몰리는 곳" (stale-answer-notice=true)
→ 내보내기 버튼을 눌러도 직전 질의("생활인구 많은 동")의 보고서가 그대로 나간다.
→ 파일 안 어디에도 "주말" 언급이나 "이 질의에는 답하지 못했다"는 표시가 없다.
```
화면에는 stale-answer-notice가 정확히 뜨지만, 사용자가 그 상태에서 내보내기를 누르면 **아무 경고 없이 이전(무관한) 질의의 보고서 파일을 받는다.** 파일만 보면 "주말" 질의에 정상 답한 것처럼 보인다.

## Section 2. 안내 문구 충돌 — 모순 없음(6건 전부 확인)

```
[범위밖+차원+시설+비율] "부산 주말 편의점 상위 10%" → 범위밖 안내만 뜸, stale=true ✓
[차원+비율+시군구]     "주말에 상위 10% 소득 시군구" → 차원 안내만 뜸, stale=true ✓
[시군구불가+값조건]     "의료 취약한 시군구 100만원 이상" → 두 고지가 각각 정상 스택, stale=false(실답) ✓
[추세불가+시군구]       "세대수 늘어나는 시군구" → 한 문장에 자연스럽게 결합, stale=false(실답) ✓
[없는지표+시군구]       "출산율 높은 시군구" → 없는지표 안내(되물음), stale=true ✓
[시설+추세불가]         "학교 근처 1인가구 늘어나는 동" → 시설 안내만 뜸, stale=true ✓
```
**우선순위가 문서 기준(범위밖 > 차원 > 시설 > 값조건)과 일치했고, "답할 수 없다" 계열 문구와 순위 행이 stale 표시 없이 공존하는 모순 사례는 없었다.** 모바일 390px 스크린샷도 확인했다 — 고지가 2개 겹쳐도(③ 케이스) 줄바꿈이 깨지거나 질의창을 가리는 문제 없이 정상 렌더링됐다.

이 섹션에서 결함은 못 찾았지만, 그 과정에서 Section 1 ①·②의 "행정동/시군구" 화면 모순과 "방법론" 고착 문제를 스크린샷으로 우연히 발견했다.

## Section 3. 시군구 합산 값 정확성

| 확인 항목 | 결과 |
|---|---|
| 개수(22개) | **✗ 20개만 나온다.** "더 보기" 버튼 자체가 없어 나머지 2개를 볼 방법이 없음(Section 1-① 참고) |
| 절대량(총인구) | **확인 불가(방법론 한계).** 진주시 1위 값(1,278,931명)과 "진주시 총인구 많은 동"의 행정동 합(1,001,662, 20행 한도로 잘린 부분합)을 비교했으나, 진주시 자체가 20개 넘는 행정동을 가질 가능성이 높아 이 부분합은 애초에 진주시 전체를 대표하지 못한다. 20행 한도를 넘는 지역의 절대량 검산은 이번 방법으로는 확정할 수 없었다 |
| 비율(고령비율) | 시군구 1위(하동군) 18.52% vs 소속 행정동(13개) 단순평균 18.51% — **0.01%p 차이로 다르지만, 하동군은 행정동 간 인구 편차가 크지 않아 가중평균과 단순평균의 차이가 원래 작을 수 있다.** 이 표본만으로 "가중평균이 맞다"를 확정하기엔 근거가 약하다 — 인구 편차가 큰 시군구(예: 창원시)로 재검증하면 더 명확해질 것 |
| 결측 제외 | 1인가구 시군구도 20/20, 총인구 시군구도 20/20 — **20행 한도에 가려 결측 제외 효과 자체를 관찰할 수 없었다.** 22개 중 정말 결측으로 빠지는 시군구가 있는지 이 방법으로는 못 봄 |
| 지역 한정 + 시군구 | "김해 시군구별 인구" → 1행("김해시"만) — **정상.** 김해는 시군구 단위에서 자기 자신 하나뿐이라 1행이 맞다. 다만 안내 문구가 "김해 안"이라는 지역 한정 표현 없이 그냥 "기준월 총인구가 많은 시군구 순입니다"라고만 나와, 지역 필터가 실제로 걸렸는지 문구만으로는 알기 어렵다(결과 자체는 맞다) |

**결론**: 20행 캡이 Section 3 검증 대부분을 가로막았다. 개수·결측 확인은 이 캡 때문에 원천적으로 불가능했고, 절대량·비율 검증도 완전하지 못했다. **20행 캡을 22행(혹은 "더 보기")으로 여는 것이 다음 검증의 전제조건이다.**

## Section 4. 비율 조건의 단위별 정확성

```
행정동 상위 10% : 화면 31행 (305×0.1=30.5 → 올림 31) ✓
시군구 상위 10% : 화면 3행  (22×0.1=2.2 → 올림 3)   ✓
격자 상위 10%   : 화면 175행 ✗ (문서 가정 127과 불일치)
행정동 하위 5%  : 화면 16행 (305×0.05=15.25 → 올림 16) ✓
시군구 하위 5%  : 화면 2행  (22×0.05=1.1 → 올림 2)   ✓
```

**격자는 결함이 아니다 — 모수 자체가 문서 가정과 다르다.** "격자 소득 낮은 블록"(필터 없음)을 직접 확인하니 **전체 격자가 1,267개가 아니라 1,750개**였다. 1,750 × 10% = 175, 화면 값(175)과 정확히 일치한다. 지시서(SONNET-NEXT-3.md)의 "격자 1267개" 가정이 구버전 수치였던 것으로 보인다 — 올림 계산 로직 자체는 4개 케이스 전부 정확했다.

## 판단이 필요한 것

1. **[Section 1-①] sgg 화면 패널 요약문이 "행정동"으로 고정** — `query-notice`는 맞는데 결과 패널 자체의 요약 문장이 틀리다. 어느 함수가 이 문장을 만드는지 특정하지 못했다(export-csv.ts의 `regionUnitLabel`과는 별도 경로로 보임) — 다음 세션에서 위치 특정 필요.
2. **[Section 1-①] 20행 캡 + "더 보기" 없음** — sgg 5개 지표 전부 22개 중 20개만 보여주고 확장 수단이 없다. 이게 표시 로직(requestedLimit 기본값)인지 UI 렌더링 한도인지 확인 필요. Section 3 검증 전체가 이것 때문에 막혔다.
3. **[Section 1-②, 신규] "방법론" 패널이 공공 도구 전체에서 항상 의료취약지수 공식만 표시** — 이번 세션 작업과 무관한 기존 결함으로 보인다. 영향 범위(민간 큐브 레이어는 정상, 공공 tool-registry 경로 전부 영향)가 넓어 다음 세션 최우선 후보로 제안한다.
4. **[Section 1-③] CSV/MD가 비율(%) 필터를 무시하고 전체 데이터를 내보냄** — 화면(필터됨)과 파일(안 됨)이 다른 데이터를 준다. 사용자가 화면 보고 다운받으면 기대와 다른 파일을 받는다.
5. **[Section 1-④] 공유 링크가 sgg·비율 조건을 URL에 구조화해 싣지 않고 원문 텍스트 재파싱에 의존** — 복원이 아예 안 되거나(빈 화면) 엉뚱한 답으로 복원된다. 링크 포맷에 `adminLevel`·`percentile` 같은 필드를 추가하는 설계가 필요해 보인다.
6. **[Section 1-⑤] CSV/HWP의 `row.note`가 2번째 동반 지표를 담지 못함** — 코드는 지표 2개를 붙이는데 export 포맷팅이 1개만 남긴다.
7. **[Section 1-⑦] stale 상태에서 내보내기가 무경고로 이전 결과를 내보냄** — 파일만 보면 실제 질의에 답한 것처럼 보인다.
8. **[Section 3] 20행 캡 때문에 절대량 합산·결측 제외 검증을 완결하지 못함** — 다음 세션에서 캡을 풀거나(#2 해결 후) 20행 이내로 소속 행정동이 확실히 적은 소규모 시군구(예: 의령군·산청군)로 표본을 바꿔 재검증 필요.
9. **verify-d.mjs의 절대값(원/명) 필터 기대치가 실제 구현과 어긋남** — 판정 로직은 안 고쳤다. 절대값 필터를 실제로 구현할지, 아니면 스크립트의 기대치를 "고지만 뜨면 통과"로 되돌릴지 결정 필요.
