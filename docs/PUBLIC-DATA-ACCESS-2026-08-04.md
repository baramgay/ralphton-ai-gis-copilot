## 1. 출생 요청주소 — 찾았다

포털 [15108075](https://www.data.go.kr/data/15108075/openapi.do) 페이지의 Swagger
위젯(로그인 없이 보임 — 로그인 벽 없었다)에서 그대로 읽었다:

```
Base URL: apis.data.go.kr/1741000/admmSexdBrthReg
Operation: GET /selectAdmmSexdBrthReg
```

즉 올바른 경로는 `/1741000/admmSexdBrthReg/selectAdmmSexdBrthReg`다. 코드에 있는
`admmBrthRegist`는 존재하지 않는 경로였다(5차 진단 그대로).

**오라클로 확인(1회 호출)**: `HTTP 200`, `resultCode: 0`, 정상 데이터 수신.
**이미 이 키에 승인돼 있다** — 활용신청 불필요, 코드 경로만 고치면 된다.

응답 필드 실측(활용신청 목록에는 없지만 이 김에 확인):
```
ctpvNm, sggNm, dongNm, admmCd, tong, ban, statsYm,
totNmprCnt, maleNmprCnt, femlNmprCnt
```
인구(`admmPpltnHhStus`)와 같은 통·반 행 단위, 같은 `totNmprCnt` 필드명이다.
합계 행 유무는 확인하지 않았다(과제 범위 밖 — 어댑터는 다른 세션 담당).

## 4. 못 본 것

- 출생·사망 응답에 **합계/소계 행이 섞여 있는지** 확인하지 않았다. 성/연령별
  분해라면 단순 합산 시 부풀 수 있다(인구 API에서 이미 겪은 함정과 같은 모양) —
  어댑터 작성 세션이 반드시 눈으로 행을 확인해야 한다.
- 8종 모두 **자료 최신월(공개 지연)**은 확인하지 않았다. 인구는 202606까지 됐다고
  알려져 있으나 출생·사망도 같은지는 별도 확인이 필요하다.
- 세션 시작 시 남아 있던 `.probe-deaths.mjs`·`.probe-deaths2.mjs`(다른 세션이 만든
  것으로 보이는 임시 파일)를 `public-api-access.mjs`로의 승격 과정에서 지웠다.
  사망 어댑터 세션이 그 파일들을 계속 쓰고 있었다면 다시 만들어야 한다 — 겹치지
  않으려다 오히려 지운 셈이라 이 자리에 밝힌다.
- `admmSexdBrthReg`의 페이지 수·건수 상한(`numOfRows` 최대치)은 확인하지 않았다.
