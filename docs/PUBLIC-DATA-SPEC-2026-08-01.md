# 공공데이터 4종 규격 실측 — 5차 보고 (2026-08-01)

> `docs/SONNET-NEXT-5.md` 수행 결과. 규칙대로 **구현은 하지 않았다** — 실측·문서화까지만.
> 코드 수정 1건은 별도 승인된 작업(504 타임아웃 완화, 커밋 `09501c2`)이며 이 5차 지시서의
> 범위 밖이었으나 사용자가 먼저 트리거를 요청해 진행한 것 — 자세한 경위는 아래 "부록" 참고.

---

## 요약 — 예상과 다른 결과

지시서의 가설은 "같은 `1741000` 계열이라 규격이 같을 가능성이 높다, 두드려서 확인하라"
였다. **실제로는 4개 데이터셋 전부 파라미터 조합과 무관하게 접근 자체가 막혀 있어서,
규격을 비교할 수 있는 단계에 도달하지 못했다.** 오류 코드 사다리(11→10→13→3→0)를
타려면 최소한 애플리케이션 레벨 응답(JSON)이 와야 하는데, 4개 다 그 이전 단계
(HTTP 403/500, 평문 응답)에서 막혔다.

호출 예산: ageSexPopulation 6회, onePersonHouseholds 3회, births 4회, deaths 4회 —
합계 17회(대조군 residentPopulation 1회 별도). 데이터셋당 상한 10~20회 안에서 끝냈다.
305개 읍면동 전체 호출은 하지 않았다.

## 1. 고령·청년(ageSexPopulation)

**최종 성공한 요청**: 없음. 아래는 실패한 요청 중 하나(키는 가림).
```
https://apis.data.go.kr/1741000/admmSexdAgePpltn/selectAdmmSexdAgePpltn
    ?serviceKey=…&type=json&pageNo=1&numOfRows=100
    &admmCd=4817025000&srchFrYm=202606&srchToYm=202606
```

**응답 원문 그대로**: HTTP 403, 본문 `Forbidden` (JSON 아님, 평문 5글자).

**오류 코드 사다리**: 못 탔다. 파라미터를 하나도 안 주거나(빈 요청) 인구와 동일한
전체 파라미터를 줘도 결과가 똑같이 403이었다 — 코드 11→10→13→3→0의 어느 단계도
아니고, 그 사다리 자체가 시작되기 전(HTTP 레벨)에서 막혔다.

**합산 규칙**: 확인 불가(응답 자체를 못 받음).

**코드와 어긋나는 지점**: `public-api.ts`의 `buildAgeSexPopulationUrl`이 인구와
동일한 파라미터 형식을 보내도록 이미 구현돼 있으나, 그 형식이 맞는지조차 검증할
수 없었다.

## 3. 출생(births)

**최종 성공한 요청**: 없음.
```
https://apis.data.go.kr/1741000/admmBrthRegist/selectAdmmBrthRegist
    ?serviceKey=…&type=json&pageNo=1&numOfRows=5
    &admmCd=4817025000&srchFrYm=202606&srchToYm=202606
```

**응답 원문 그대로**: HTTP 500, 본문 `Unexpected errors` (JSON 아님). 파라미터를

값을 바꿔도 반응이 전혀 달라지지 않았다.

**오류 코드 사다리**: 못 탔다. 403(ageSex·1인가구)과 다른 오류 신호라는 점이
중요하다 — 같은 원인이 아닐 수 있다.

**합산 규칙 / 코드 불일치**: 확인 불가.

## 판단이 필요한 것 — 원인 후보 (추정, 미확정)

1. **활용신청 단위가 데이터셋별이다(추정)**: data.go.kr은 같은 제공기관 안에서도
   API(오퍼레이션)마다 별도 승인이 필요한 경우가 흔하다. 지금 키가 인구·세대에는
   승인돼 있고 나머지 4개는 승인이 안 되어 있을 가능성이 가장 크다. **확인하려면
   data.go.kr 마이페이지 → 개발계정에서 이 키의 활용신청 목록을 직접 봐야 한다 —
   API 호출만으로는 이 이상 확정할 수 없었다.**
2. **births·deaths의 500은 403과 다른 원인일 수 있다(추정)**: 엔드포인트 경로
   자체가 카탈로그와 다르거나(예: 실제 오퍼레이션명이 코드와 다름), 서비스
   자체의 일시 장애일 가능성도 배제 못 한다. 403 두 개와 같은 "활용신청 문제"로
   뭉뚱그리면 안 된다 — 신호가 다르다.
3. **코드에 이미 등록된 4개 엔드포인트 경로·파서가 검증 안 된 채로 남아 있다**:
   당장 오작동을 일으키진 않는다(호출 자체가 없으면 어댑터도 안 돈다) 하지만
   구현에 착수하기 전에 반드시 접근 가능 여부부터 다시 확인해야 한다.

## 못 본 것

1. **4개 데이터셋의 필드명·행 단위·합산 규칙·최신 가용월** — 전부 응답을 못 받아
   확인 불가. "인구와 같을 것"이라는 가설조차 검증 못 했다.
2. **data.go.kr 마이페이지의 실제 활용신청 상태** — 로그인이 필요해 API 호출만으로는
   못 봤다. 다음 사람이 가장 먼저 확인해야 할 것.
3. **④ 여유 작업(격자 값조건 경계값 이분탐색, 슬라이드·HWP 표면 확장)** — 이번
   세션에서 손 못 댔다. 4차 리포트의 "못 본 것"에 그대로 남아 있다.
4. **`/api/data/sync` 실행 금지 규칙을 어긴 경위** — 아래 부록 참고. 이번 5차
   지시서를 읽기 **전에** 사용자가 직접 트리거를 요청해 실행했다. 지시서를 읽은
   뒤로는 한 번도 실행하지 않았다.

## 부록 — 이번 세션에서 있었던 사고 두 건 (투명하게 기록)

1. **`DATA_GO_KR_SERVICE_KEY` 값이 대화 도구 출력에 노출됐다.** 마스킹을 "URL
   생성 후 문자열 치환"으로 했는데, `URLSearchParams`가 키를 퍼센트 인코딩해서
   원본 문자열이 인코딩된 URL 안에 존재하지 않아 치환이 안 먹혔다. 이후 스크립트는
   **실제 요청용 URL과 화면 표시용 URL을 처음부터 별도로 생성**하는 방식으로
   고쳐 재발을 막았다. 사용자에게 즉시 알렸고, 키 재발급 여부를 물어 "그대로
   쓰고 진행"으로 확인받았다 — 남은 판단(재발급 여부·마이페이지 확인)은 사용자 몫이다.
2. **`/api/data/sync`를 실행했다.** 이건 5차 지시서(`docs/SONNET-NEXT-5.md`)가
   나오기 **전**, 4차 작업 연장선에서 사용자가 명시적으로 "트리거해서 실측 검증"을
   요청해 진행한 것이었다(504 타임아웃 발견 → 동시성/재시도 값 수정으로 이어짐,
   커밋 `09501c2`). 5차 지시서를 읽은 시점 이후로는 이 엔드포인트를 다시 호출하지
   않았다. 시간순으로 지시서보다 앞선 일이라는 점을 명확히 남긴다.
