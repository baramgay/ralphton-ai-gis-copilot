## 고친 것 (배포·재검증 완료)

### 1. 방향 낱말 목록 비대칭 — `커지`·`많아지`·`하락`·`떨어지`·`작아지`·`적어지`

**질의 원문 / 화면 글자(수정 전)**
```
"총인구 커지는 동"     → "기준월 총인구가 많은 행정동 순입니다."  (조용히 수준 순위)
"고령비율 하락하는 동" → "고령인구 비율이 높은 행정동 순으로 정렬했습니다." (조용히 수준 순위)
"출생 많아지는 동"     → "기준월 출생 수가 많은 행정동 순입니다." (조용히 수준 순위)
```
**어느 표면**: 화면 안내(query-notice) — 라우팅 단계.

**코드에서 확인한 원인**: `NEGATED_DIRECTIONS`(`query-catalog-meta.ts:155-159`)는 이 6개 낱말을
이미 방향어로 다루는데, `query-signals.ts`의 growth/decline 감지 목록(468-517행)엔
없었다. "부정문 중화" 쪽은 알아듣고 "방향 감지" 쪽은 못 알아듣는 비대칭 — 지시서가
예시로 든 "오르"(직전 커밋에서 이미 고침)와 정확히 같은 유형이다.

**심각도**: 조용히 틀린 답 — 이미 존재하는 추세 도구(`rankPopulationGrowthPressure`
등)를 놔두고 수준 순위로 답했다. 사용자는 "커지는"이라고 물었는데 "많은"으로 답을
받는다는 걸 알아채기 어렵다.

**조치**: `query-signals.ts` growth/decline 목록에 6개 낱말 추가. 유닛테스트 6건
신설(`tests/analysis/query-signals.test.ts`) — 결함 주입(수정 전 코드로 되돌려 실행)
으로 전부 실패함을 먼저 확인했다. 배포 후 prod 재실측:
```
"총인구 작아지는 동" → "12개월 인구 감소율이 높은 행정동 순으로 정렬했습니다." ✓
"세대수 커지는 동"   → "...늘고 주는 변화는 이 지표로 아직 낼 수 없어 지금 수준으로 답했습니다." ✓(정직한 한계 고지)
```
커밋 `1002a4e`.

**부수 발견(수정 안 함) — 고령비율 추세 도구의 방향 무시**: 위 수정을 배포하고 나니
"고령비율 하락하는 동"·"떨어지는 동"이 이번엔 **`rankElderlyRatioTrend`로 라우팅은
되는데, 그 도구 자체가 항상 "많이 오른" 순으로만 답한다**("고령비율이 12개월간
많이 오른 행정동 순입니다").

```
"고령비율 줄어드는 동" → 상승 도구 답(수정 이전부터 있던 낱말 "줄어"로 재현됨 — 내가 만든 결함 아님)
"고령비율 감소하는 동" → 동일
```

**코드에서 확인한 원인**: `tool-registry.ts:558` `rankElderlyRatioTrend`는
`ranked(analyzed, "descending", ...)`로 방향이 하드코딩돼 있고, `query-catalog.ts:156`
`scoreExtra`는 `growth`든 `decline`이든 구분 없이 같은 점수를 준다. **하락 방향
전용 도구가 아예 없다** — `rankPopulationGrowthPressure`/`rankPopulationDeclineRisk`처럼
쌍으로 존재하는 인구 추세와 달리, 고령비율 추세는 상승 쪽 하나뿐이다.

**심각도**: 조용히 틀린 답에 가깝다(다만 안내문 자체는 "오르는"이라고 정직하게
말하므로, 주의 깊게 읽으면 방향이 다르다는 걸 알 수 있다 — 순수 은폐는 아니다).
**"줄어"/"감소하"로도 재현되므로 이번 세션 수정으로 새로 생긴 게 아니라 원래 있던
결함이다.** 새 도구 신설 또는 기존 도구의 방향 파라미터화가 필요해 "고쳐도 되는 것"
범위를 넘는다고 판단해 **손대지 않고 판단이 필요한 것에 남긴다.**

### 2. 시군구 합산 결과가 여전히 "행정동"으로 표기

**질의 원문 / 화면·CSV 글자(수정 전)**
```
"총인구 많은 시군구"
  화면 안내: "기준월 총인구가 많은 시군구 순입니다."  ← 맞음
  CSV 머리글: "순위,행정동코드,시도시,이름,값,비고"   ← 틀림
  MD/HWP/슬라이드 요약: "대상 행정동 22개 중 상위 10개 제시"  ← 틀림
```
**어느 표면**: CSV·리포트(MD)·HWP·슬라이드 — 화면은 정상, 내보내기 4종이 전부 틀림.

**코드에서 확인한 원인**: `export-csv.ts:54` `regionUnitLabel()`은 코드가 **정확히
5자리**일 때만 "시군구"로 본다. 그런데 공공 도구 합산(`tool-registry.ts:184-185`
`rollupToDistricts`)은 "행정동 코드 10자리 규약을 지키되 시군구임을 알 수 있게 뒤를
0으로 채운다"는 설계로 `"4817000000"`(5자리+00000) 형태를 쓴다. 민간 레이어 집계
(`aggregate.ts:3-5` `sggCode`)는 진짜 5자리(`"48170"`)를 쓴다 — **같은 "시군구"를
두 가지 다른 코드 형태로 표현하는데, 판별 함수는 한쪽만 알아봤다.**

**심각도**: 조용히 틀린 답 — 화면에서 "시군구 22개"라고 정확히 읽은 사용자가
CSV·보고서를 내려받으면 "행정동 22개"라고 적혀 있어 파일만 보고 오인할 수 있다.
공공기관 보고서에 그대로 옮기면 틀린 단위가 실린다.

**조치**: `regionUnitLabel()`이 "5자리" 또는 "10자리이며 뒤 5자리가 00000"인 코드를
모두 시군구로 인식하도록 수정. 실데이터(305개 행정동 코드) 전수 확인 결과 "00000"으로
끝나는 진짜 행정동 코드는 0건이라 오검출 위험 없음을 확인. 유닛테스트 2건 추가,
결함 주입으로 실패 확인 후 수정 반영. 배포 후 재실측:
```
CSV 머리글: "순위,시군구코드,시도시,이름,값,비고" ✓
MD/HWP/슬라이드: "대상 시군구 22개 중 상위 10개 제시" ✓
```
커밋 `13a628c`.

## Section 3 — 조건 조합 5건

지시서가 지정한 조합을 그대로 돌렸다. **5건 전부 조건이 조용히 사라지지 않았다.**

```
"총인구 많은 시군구 상위 10%" → 3행 (22×10%=2.2→올림 3) ✓
"소득 400만원 이상인 시군구"  → 0행, 고지 "조건에 맞는 곳이 없습니다(데이터가
                                없는 것이 아닙니다). 전체 1위는 창원시성산구
                                362.12만원/월입니다." ✓ (정직한 0건 disclosure)
"생활인구 많은 격자 5곳만"    → 5행 정확히 ✓
"고령비율 상승하는 시군구"    → 22행(시군구 개수 캡 없음 확인) ✓
"격자 소득 700만원 이상"      → 0행, 동일한 정직 고지 패턴 ✓
```
기존 `combo.mjs`(9건, 값조건×교차/다중조건/격자/시군구/추세 조합)도 재확인 —
전부 조건 소실 없이 필터되거나 "걸 자리가 없다"고 정직하게 밝힘.

**못 본 것**: 격자 값조건이 "0건"과 "전체(24행, 사실상 무필터)" 양극단만
확인됐고, **그 사이(1~23행)로 부분 필터링되는 임계값**은 직접 확인하지
못했다. 시간상 이분 탐색으로 정확한 경계값을 못 찾았다 — 다음 세션 후보.

## Section 4 — 되물음이 필요한 자리

```
"인구 많고 소득 높은 동"   → 확정 답변(교차분석 both 모드)
"젊은 동"                 → 되물음: "혹시 「청년 소비비중」인가요?"
"살기 좋은 동"             → 전면 거부: "질문을 해석했지만... 예시를 넣어 주세요"
"발전 가능성 있는 지역"    → 전면 거부(위와 동일 문구)
```

**"인구 많고 소득 높은 동"은 실제로는 모호하지 않다.** 이 앱은 2개 지표는
"교차분석"(둘 다 높음, both 모드), 3개 이상은 "다중조건"으로 이미 명확히
구분해 놓았다(round8에서 검증된 규칙) — 그래서 확정 답변이 정답이다.

**"젊은 동"은 의도대로 되물었다** — 청년 비중과 고령 비율 낮음이라는 두 해석이
가능한데, 그중 하나를 확인하는 문장을 던졌다. 조용히 하나를 고르지 않았다.

**"살기 좋은 동"·"발전 가능성 있는 지역"은 되물음이 아니라 전면 거부다.**
실패는 아니다(조용히 틀린 답보다 낫다는 원칙엔 부합) — 다만 지시서가 요구한
"고를 수 있는 선택지를 문장으로 제시"하지는 않았다. 일반 사용법 예시("사망자
많은 곳" 등)만 보여줄 뿐, "혹시 소득 기준인가요? 의료 접근성 기준인가요?" 같은
구체적 분기는 없다. **버그로 보진 않는다** — "살기 좋다"는 정의 자체가 없어
구체적 선택지를 만들기 어렵다는 점도 이해된다. UX 개선 여지로만 기록한다.

**조용히 틀린 답으로 이어진 사례는 0건.**

   코드를 확인 못 했다.
