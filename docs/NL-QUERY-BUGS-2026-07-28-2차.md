## Section 1. 공공 도구 시군구(sgg) 무시 — 13개 전수 확인 완료

**결론: 13개 공공 rank 도구 중 12개가 "시군구"를 완전히 무시하고 읍면동 순위를 낸다.**

```
✗행정동 rankHospitalScarcity          "의료 취약한 시군구" → 거창군 북상면
✓시군구 rankElderlyUnderserved        "고령 인구 대비 병원 부족한 시군구" → 창원시성산구 (※ 아래 설명)
✗행정동 rankPopulationGrowthPressure  "인구가 늘어나는 시군구" → 창원시의창구 북면
✗행정동 rankPopulationDeclineRisk     "인구가 줄어드는 시군구" → 사천시 용현면
✗행정동 rankSingleHouseholdRisk       "1인가구 비중 높은 시군구" → 창원시마산합포구 진전면
✗행정동 rankDeathCount                "사망자 많은 시군구" → 창원시진해구 충무동
✗행정동 rankHouseholdCount            "세대수 많은 시군구" → 의령군 낙서면
✗행정동 rankBirthCount                "출생이 많은 시군구" → 창원시의창구 대산면
✗행정동 rankNaturalDecrease           "자연감소가 큰 시군구" → 의령군 용덕면
✗행정동 rankNaturalIncrease           "자연증가가 큰 시군구" → 통영시 산양읍
✗행정동 rankPopulationDensity         "인구밀도 높은 시군구" → 양산시 양주동
✗행정동 rankPopulationSize            "인구가 많은 시군구" → 창원시의창구 북면
✗행정동 rankElderlyRatio              "고령화율 높은 시군구" → 진주시 정촌면

시군구 집계 성공 1 / 13
```

**유일한 "성공"(rankElderlyUnderserved)도 사실은 성공이 아니다.** 안내문이 "교차분석 · 고령비율(공공) 대비 의료취약지수(공공) — 22개 시군구"로, `resolveCrossQuery`(민간+공공 교차 경로)가 대신 가로챈 것이다. rank 도구 자체가 sgg를 지원하는 게 아니라, "고령"+"병원 부족" 두 단어가 교차분석 트리거로도 걸려 우연히 다른 경로로 샌 것.

### 원인
13개 도구 전부 `query-catalog.ts`에서 동일한 패턴을 쓴다:
```js
build: (s) => scopeFilters({}, s),
```
`scopeFilters()`(`query-catalog.ts:34-51`)와 그 아래 `scopedRegions()`(`tool-registry.ts:133-140`)는 질의에 적힌 **지역명**(창원·김해 등)으로 필터링만 한다. `adminLevel`/`sgg` 개념 자체가 이 경로에 없다. "시군구"라는 단어는 어떤 신호로도 감지되지 않고(`query-signals.ts` 전체를 확인했으나 "시군구" 관련 cue 없음), 그냥 305개 읍면동 전체를 대상으로 계산한 뒤 결과를 그대로 낸다.

대조: 민간 큐브 경로(`resolve-layer-query.ts`)에는 `detectAdminLevel()`(193-198행)과 `aggregateToSgg()`(`aggregate.ts:13`)가 있어 시군구 집계가 실제로 동작한다. 공공 경로엔 이 대응물이 전혀 없다 — 이번 코드 조사에서 `aggregateToSgg`를 호출하는 곳은 민간 레이어 경로뿐임을 확인했다.

### 집계 가능성 확인
비율 지표(고령화율·1인가구비율)를 시군구로 올리려면 단순 합산이 아니라 **인구가중평균**이어야 한다. 공공 경로(`tool-registry.ts`)에는 그런 가중평균 로직 자체가 없다 — `scopedRegions()`가 반환하는 건 필터링된 읍면동 레코드 배열일 뿐, 상위 단위로 합산·가중평균하는 코드가 없다. 즉 "단위 표시만 바꾸면 되는" 문제가 아니라, **시군구 집계 파이프라인을 공공 경로에 새로 만들어야 하는 규모**다.

### 왜 위험한가
1위로 나오는 이름이 실재하는 읍면동이라(예: "거창군 북상면") 사용자가 "이게 시군구 답이 아니다"를 알아채기 어렵다. "고령화율 높은 시군구"에 읍면동 순위를 주면 그대로 보고서에 들어갈 수 있다 — SONNET-NEXT.md가 우려한 그대로다.

## Section 2. 변주 코퍼스 — 13레이어 × 6틀 = 78건

**지시서는 레이어당 대표지표 2개, 틀 12개를 요청했으나 시간 예산상 레이어당 1개 지표 × 6개 틀(78건)로 축소했다.** 지시서 자체가 "전수는 오래 걸리니 대표로 시작, 실패율 높은 레이어만 확장"이라고 명시했고, 아래처럼 실질 실패가 0이라 확장하지 않았다 — **축소 사실과 근거를 명시한다.**

```
지표별: 12/13 만점, 총인구만 5/6 (틀5 "총인구 늘어나는 동" 실패로 표시)
틀별:   틀0~4 13/13, 틀5("{지표} 늘어나는 동") 12/13
총 78건 실행
```

**"총인구 늘어나는 동" 실패는 검사 스크립트의 오탐이지 실제 결함이 아니다.** 안내문이 "12개월 인구 증감률이 높은 행정동 순"이라 "총인구"라는 리터럴 문자열이 없어서 내 판정 스크립트(문자열 포함 검사)가 실패로 찍었을 뿐이다. 실제로는 `resolve-trend-query.ts:64-66` 주석에 명시된 **의도된 설계**대로 동작한 것 — 공공 인구는 전용 도구(`rankPopulationGrowthPressure`)로 가고, 그 안내문이 "총인구" 대신 "인구 증감률"이라는 표현을 쓸 뿐이다.

**결론: 이번 78건 표본에서는 매칭 방식 자체의 계통적 실패가 발견되지 않았다.** 1차 리포트에서 발견된 격자 붙여쓰기 등의 문제는 이미 고쳐진 상태로 확인됐다(회귀 verify-b/verify-batch에서도 재확인).

## Section 3. 재현만 됐던 #10·#11·#13 원인 확정

### #11 — "카드매출이 늘지 않은 동" (부정문)

```
카드매출이 늘어난 동     → ✓ 카드매출(NH) 증가 추세
카드매출이 늘고 있는 동  → ✓ 카드매출(NH) 증가 추세
카드매출이 늘지 않은 동  → ✗ 카드소비 · 카드매출 레이어(단일 수준, 조건 무시)
카드매출이 줄어든 동     → ✓ 카드매출(NH) 감소 추세 (대조군)
카드매출이 줄지 않은 동  → ✗ 단일 수준 (동일 패턴)
```

**원인**: `resolve-trend-query.ts:38`
```js
const RISING_CUES = ["증가", "늘어", "늘고", "늘어나", "상승", "오르", "성장", "커지", "많아지"];
const FALLING_CUES = ["감소", "줄어", "줄고", "줄어드", "하락", "떨어지", "축소", "작아지", "적어지"];
```
"늘지"/"줄지"라는 활용형이 어느 목록에도 없다. `detectDirection()`(41-47행)이 `null`을 반환하면 `resolveTrendQuery` 자체가 `null`(105행)이 되어 트렌드 경로를 아예 안 탄다 — 부정문이라서 틀리는 게 아니라 **활용형이 cue 사전에 없어서 애초에 트렌드 질의로 인식조차 안 되는 것**이다.

**주의(판단 필요)**: "늘지"를 cue에 그냥 추가하면 "늘지 않은"이 rising으로 오판된다. 이 사전에는 부정 어미("~지 않다") 인식 로직이 전혀 없기 때문이다. 제대로 고치려면 cue 추가가 아니라 부정 인식 로직 신설이 필요할 수 있다.

### #10 — "%"·"원" 단위 임계값

```
평균소득 상위 5곳          → ✓ 5행 (절대개수, 대조군 — 정상)
평균소득 상위 10%          → ✗ 24행 (조건 무시)
평균소득 100만원 이상인 동  → ✗ 24행 (조건 무시)
평균소득 300만원 넘는 동    → ✗ 24행 (조건 무시)
```

**원인**: `resolve-layer-query.ts:165` `COUNT_UNITS = ["곳", "군데", "동네", "개"]` — `detectResultCount()`(174-191행)는 정수 개수 단위만 인식한다. %(퍼센트)나 "만원"/"원" 같은 절대 금액 단위를 다루는 코드는 프로젝트 전체에서 찾지 못했다. **기능 부재 확정** — 라우팅이 잘못된 게 아니라 애초에 그런 필터를 만드는 기능이 없다.

### #13 — "고령비율 상승하는 곳" (추세)

```
고령비율 높은 동       → (대조군) 고령인구 비율 순
고령비율 상승하는 곳   → 고령비율 높은 동과 완전히 동일한 결과
고령비율 늘어나는 곳   → "12개월 인구 증감률" (총인구 증감 — 고령과 무관한 답)
인구 늘어나는 곳       → (대조군) 정상 작동
```

**두 가지가 겹쳐 있다:**

1. "상승"이라는 단어가 `query-signals.ts:469-483`의 growth cue 목록(증가/늘어/증가하/성장/유입/늘고/증가세/몰리)에 없다. 그래서 "고령비율 상승하는 곳"은 growth 신호가 전혀 안 잡히고 elderly 신호만 잡혀 그냥 정적 순위(`rankElderlyRatio`)로 간다.

2. "늘어"는 growth cue에 있어서 잡히지만, **고령비율 전용 추세 도구가 아예 없다.** `TOOL_CATALOG`에는 `rankElderlyRatio`(정적)와 `rankPopulationGrowthPressure`(총인구 추세)만 있다. "고령비율 늘어나는 곳"은 growth 신호와 elderly 신호가 동시에 잡히는데, `query-catalog.ts`의 점수 계산을 손으로 따라가 보면:
   - `rankPopulationGrowthPressure`: baseScore 35 + cueBonus 20 + (growth 매치 +32) = **87**
   - `rankElderlyRatio`: baseScore 30 + cueBonus 18 + ("비율" 포함 +36) = **84**

   3점 차로 총인구 증가 도구가 이겨서, "고령비율"이라는 단어를 완전히 무시한 채 전혀 다른 질문("총인구 늘어나는 곳")에 답한다.

**분류**: 순수한 "라우팅 문제"(있는데 안 탐)도, 순수한 "기능 부재"(막혀서 아무것도 안 나옴)도 아니다. **"전용 기능이 없는 자리에서, 무관한 두 일반 도구가 점수 경쟁을 벌이다 근소한 차이로 엉뚱한 쪽이 이겨 그럴듯한 오답을 낸다"**는 제3의 유형이다. SONNET-NEXT.md가 강조한 "부재 vs 가로채기" 구분에 대입하면 가로채기 쪽에 가깝지만, #8(가로채기 — 트리거 문자열이 우연히 포함됨)과는 메커니즘이 다르다(여기는 스코어링 근소 우위).

## 판단이 필요한 것

1. **Section 1 (공공 sgg 집계)**: 신규 파이프라인이 필요하다 — 비율 지표는 인구가중평균, 절대량 지표는 합산. 13개 도구 전체에 영향을 주는 규모라 설계 판단이 필요하다.
2. **#11 (부정문)**: cue 사전 확장만으로는 안 되고 부정 인식 로직 신설이 필요할 수 있다 — 어느 선까지 다룰지 판단 필요.
3. **#13 (지표별 추세)**: 고령비율처럼 "정적 지표는 있는데 추세 도구는 없는" 지표가 몇 개나 더 있는지, 개별 추세 도구를 다 만들지 범용 매칭으로 통합할지는 설계 판단이 필요하다. (참고: 공공 지표 중 elderly_ratio·density·households 등도 같은 사각지대일 가능성 — 이번 세션에서 전수 확인은 안 함)
4. **`.prod-verify-c.mjs`의 타이밍**: "창원 김해 진주 중 어디가 나은가"·"세대수 많은 동" 케이스가 3번 중 2번 "의도 파악 중…"(로딩 중간 상태)로 잡혔다. 첫 실행(이 세션이 병렬 부하를 쌓기 전)에는 정상 통과했다. 격리 재실행에서도 재현된 걸 보면 세션 내 누적된 좀비 프로세스(20개+) 영향일 가능성이 크지만 완전히 배제는 못 했다. 스크립트의 고정 1800ms 대기를 폴링 방식으로 바꾸는 게 근본 해결일 수 있다 — **제품 코드 문제로 보지 않는다.**
